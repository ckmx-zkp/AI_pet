# 04 — ESP32 固件（身体层）设计缺口分析

> 用途：AI Pet 四仓设计缺口分析之固件篇。市场依据引用同目录 `00-AI宠物市场与竞品调研.md` 的"启示 1~6"。
> 代码事实来源：`ESP32_XIAOZHI/xiaozhi-esp32/` 的 `AI_PET_DEV_PLAN_zh.md`、`AI_PET_PROGRESS_zh.md`、`2026-07-18_后续开发规划_需二次审阅.md`、`main/pet/` 骨架，以及 `work_dashboard/AI-Pet固件联调看板.md`。
> 撰写时间：2026-08-01。固件现状：M0/M1 完成，M2 单眼已点亮（右眼未接），M3/M4 未开始，M5 部分（5 个眼睛 MCP 工具已真机验证）。

## 1. 项目定位一句话回顾

AI Pet = "星座×MBTI 人设 + 可审计记忆"的桌面 AI 电子宠物；固件是其**身体层**——人设的表达执行器（眼睛/灯带/舵机/语音链路），人设与记忆真源在云端，硬件负责"把人设演出来"并产生"生命感"。

## 2. 已有设计的市场契合度

以下已做/已规划的方向与市场验证过的打法同构，**应保持、不要回退**：

- **魔眼动效 ≈ LOVOT/Ropet 眼神系统的低成本复刻**。GC9A01 圆屏 + 情绪整帧切换（C1 架构）+ 视线/眨眼，对应"眼神追踪+瞳孔变化"这一留存之王的核心表达器官（启示 5）。方向正确。
- **情绪联动对话**（ASR→LLM→`set_emotion`→TTS）已端到端跑通，证明"人设驱动身体表达"链路成立。
- **MCP 工具化外设**（`self.eye.*`，仿 `LampController`，服务端只路由）= 云端人格可实时操纵身体，为 persona_pack 表达参数落地留好了管道，契合赛道文档"硬件=表达执行器"分层。
- **PetBehaviorController 仲裁架构**（优先级+TTL+锁定，`pet_behavior_types.h` 骨架已含 `BehaviorSource/Priority`）是行业级的正确骨架：Eyes/Head/Led 统一意图帧，避免三套外设各自读 `Application` 状态。
- **K230D 双通路视觉规划**（被动拍照上云 + 本地人脸/情绪实时事件）是 Ropet"鼻子藏传感器"路线的等价物，且隐私叙事更好（本地推理、结构化结果、不存图）。
- **不显示聊天字幕/UI 的决策**与"防助手化"（启示 4）一致：没有屏幕文字，用户就不容易把它当语音助手。

结论：固件的技术骨架不输给竞品方案，**缺口不在"怎么表达"，而在"表达什么"——目前只能被动应答，没有情感回路**。

## 3. 设计缺口清单

### G1 无触摸交互 —— 身体层最大缺口 【P0】

- **缺口描述**：固件规划（DEV_PLAN、后续规划、Kconfig 全量配置项）中**没有任何触摸/压力/接近传感器**。AI Pet 板型甚至主动关闭了 7B 原板的 GT911 触摸路径。摸头、拥抱、戳一戳全部无感知。
- **市场依据**：LOVOT（求抱+体温）、Ropet（鼻子藏传感器+37°C 恒温）、Moflin（抚摸养成）均把抚摸反馈作为情感回路核心；"陪伴不一定是语言"（启示 5）、"被需要感"（启示 1）都需要一个用户主动施予、宠物即时回应的物理通道。Ropet 退货率 <4% 与其多模态身体反馈直接相关。
- **影响**：交互只剩语音一条腿。语音是"助手"的通道，抚摸才是"宠物"的通道——缺它则产品在品类上滑向"会眨眼的智能音箱"，正面撞上启示 4 的助手化陷阱。
- **建议方向**：BOM 级方案即可，不追求电子皮肤：① 头部 1~2 路电容触摸（TTP223 或 ESP32 原生 touch pad，扩展座尚有空闲 GPIO）区分"摸头/拍头"；② 可选一路薄膜压力传感器做"抱"。信号接入 `PetBehaviorController` 作为新 `BehaviorSource::kTouch`，优先级介于 vision 与 MCP 之间，触发开心/呼噜/蹭头等组合反馈。
- **优先级**：P0（涉及结构件与 BOM，越晚改代价越大）。

### G2 无 idle/主动行为，无"自发性"设计 【P0】

- **缺口描述**：当前唯一入口是唤醒词（+未来 K230 人脸门控的 `WakeWordInvoke`）。`PetBehaviorController` 的输入源（DeviceState/MCP/视觉/空闲定时器）全是**反应式**的；`auto_idle_` 甚至被默认关闭（为调试）。宠物不会无聊、不会求关注、不会在用户回家时有反应（除非看见脸），被冷落后不会低落。
- **市场依据**：LOVOT 的第一变量是"主动性设计——它先来找我"（启示 1）；EMO 的"按心情决定做什么"证明自主行为=生命感（启示 2）；完全被动的设备没有"它在等我"的叙事。
- **影响**：无人互动时产品呈现为"关机的玩具"，恰是"吃灰"体验的开端（市场核心矛盾）。
- **建议方向**：在 `PetBehaviorController` 增加**自发行为引擎**：内部状态量（精力/心情/亲密度，NVS 持久化）+ 时间驱动（久未互动→四处看/打哈欠/灯带渐暗"无聊"）+ 事件驱动（K230 发现人脸→主动注视+开心）。第一阶段**纯身体语言、不开口**，避免与"服务端无主动下推通道"的缺口耦合；开口留待 xiaozhi 侧主动会话能力就绪。
- **优先级**：P0（软件改动为主，不依赖新硬件，可并行启动）。

### G3 行为完全确定性，无随机性与个体演化 【P1】

- **缺口描述**：情绪→帧、状态→灯效、状态→舵机全是静态映射表（后续规划 §6.3 自动映射表即确定性表）；同星座同 MBTI 的两台设备行为完全一致，且同一台设备行为永不变化。
- **市场依据**："被摸透了"是用户投诉第一名（启示 2）；Moflin 用 60 天养成 400 万种性格组合制造持续投入。
- **影响**：新鲜感以周计衰减；无法支撑"每只宠物独一无二"的卖点，人设差异化只停留在对话文本层。
- **建议方向**：三层注入随机性——① 表现层：眨眼间隔、漂移视线、歪头时机加抖动（廉价，先做）；② 参数层：动作幅度/速度/灯效色相按 persona（内向/外向）+ NVS 中的个体种子偏移；③ 演化层：亲密度/心情状态量随互动历史缓慢改变行为基线（依赖 G2 的状态量）。固件只存"种子+少量状态"，演化规则与审计留在云端，不违背"人设真源在云端"的分层。
- **优先级**：P1。

### G4 无端侧降级人格：断网即"死亡" 【P1】

- **缺口描述**：语音链路全在云（ASR/LLM/TTS 均服务端），断网或云服务故障时宠物无任何行为能力——不眨眼、无表情、无反应。赛道文档已建议"本地缓存 `persona_id` + 默认表情表，弱网时仍保持面孔气质"，固件未实现。
- **市场依据**：Ropet 端侧小模型离线学习主人习惯，端云混合让断网不"死"（启示 2、6 的反面教材）；离线存活也是"它是个生命"叙事的一部分。
- **影响**：家庭 WiFi 抖动、服务器维护窗口都会制造"宠物猝死"瞬间，直接破坏情感沉浸；对"可审计记忆+自建云"的可信叙事也是减分项。
- **建议方向**：**不做**端侧 LLM（P4 算力/成本均不支持），只做离线情绪行为包：NVS 缓存 persona 默认气质（默认情绪、眨眼频率、灯效元素色）+ 断网检测后进入"离线人格模式"（本地状态机驱动眼/灯/舵机，含 G2 的 idle 行为）+ 恢复联网时的"重逢"反馈。本质是 G2 自发行为引擎的断网兜底，两者应合并设计。
- **优先级**：P1。

### G5 无"被需要感"的身体表达语言 【P1】

- **缺口描述**："饿了、想你了、求摸摸"没有对应的外设语言。现有情绪集（neutral/happy/angry/sad/joy）是**应答表情**，没有**需求状态**（needy/lonely/expectant）和对应的灯效/声音/动作组合；`EmotionLabel` 骨架里也没有此类枚举。
- **市场依据**：启示 1——LOVOT 零功能留存最高，证明"宠物需要用户">"用户配置宠物"；这是本项目的"外部需求"之首。
- **影响**：即使 G2 做完，宠物也只会"自嗨"，不会"索取"；用户没有被需要的钩子，回访动机弱。
- **建议方向**：① 扩充 `EmotionLabel` 与眼睛资产：lonely/expectant/sleepy-needy 等 2~3 个需求态；② 定义组合表达范式：需求态=特定眼神+灯带慢呼吸+偶发小声（非 TTS 的提示音/呼噜声）+舵机小动作；③ 触发条件挂在 G2 的内部状态量上（久未互动→lonely；检测到主人靠近→expectant）。注意与眼资产迁移（G7）联动排期，新增帧直接落 assets 分区。
- **优先级**：P1（依赖 G2，表达资产依赖 G7）。

### G6 拟物体验 bug：误唤醒 / "休息不挂断" 【P0】

- **缺口描述**（联调看板 2026-08-01 已知问题）：① 端侧误唤醒率偏高（AFE/WakeNet 灵敏度），每次误触触发开场白，体感像故障；② 说"休息/闭眼"后 `self.eye.close` 执行但会话仍在 listening，环境声/唱歌继续被 ASR 接住——"睡着了还在偷听"，拟物一致性破裂；③ 下行 16k/设备 24k 重采样告警。
- **市场依据**：拟物一致性是"生命感"的地基；一条"睡了还醒着"的 bug 抵消十个新表情（启示 2 的反面：露馅即死）。
- **影响**：当前即影响演示与留存体验；误唤醒还放大云端 LLM/TTS 成本。
- **建议方向**：固件侧——调 WakeNet 阈值/麦增益（看板 S6 已归固件）；"close 后本地挂断会话"待拍板（看板待决），建议做，与服务端 S2 形成双保险。服务端侧 S1（关开场白）/S3（缩短无语音断连）已在看板排队，此处不重复派工。
- **优先级**：P0（联调期即应收敛，不等里程碑）。

### G7 工程现实约束：OTA 槽 92.5% + 排期挤压 【P0】

- **缺口描述**：`xiaozhi.bin` 3,881,072 B，单 OTA 槽 4 MiB 已用 92.53%，仅剩 ~306 KiB；9 张眼睛整帧（1.04 MB）仍嵌在应用镜像里。右眼、灯带、双舵机、K230 UART、行为控制器、以及本文 G1~G5 的新增代码全都要进这 306 KiB——**空间上根本排不下**。内部 SRAM 静态占用也已 83.35%。
- **市场依据**：无直接市场依据；这是所有体验缺口的**物理前提**——不解决则 P0/P1 项无法落地。
- **影响**：继续按现状堆功能会先撞 OTA 上限（新固件放不进槽 = 设备变砖风险），再撞内存红线。
- **建议方向**：严格按后续规划阶段 A 执行——眼资产迁 16 MiB assets 分区（迁后镜像约降 25%，OTA 使用率回到 ~68%）、建立 80% 体积门禁与 heap/栈水位监控。此前置完成前，G5 新资产、触摸驱动等新代码不合并主线。
- **优先级**：P0（一切新增功能的前置）。

### G8（补充）外设状态不上报，云端不知道"身体在干嘛" 【P2】

- **缺口描述**：联调看板集成点 #9"外设状态上报"未开始（依赖 backend 501）。眼睛当前情绪、舵机位、在线/离线人格模式等身体状态只存在于端上；`PetRuntimeSnapshot` 骨架已有但无上报路径。
- **市场依据**：记忆主动召回（启示 3）需要上下文——"下午你摸了它三次"这类身体事件是记忆素材；也是可审计叙事的一部分。
- **影响**：云端人设与端上表达无法对账（admin 无法对表，赛道文档 V0.3"状态回读"目标落空）；亲密度等状态量缺云端镜像，换机/OTA 后丢失。
- **建议方向**：`PetRuntimeSnapshot` 低频快照经 xiaozhi 旁路转 backend；身体事件（被摸、重逢）作为 memory candidate 素材。等 backend 接口转可用后做，勿抢跑。
- **优先级**：P2。

### G9（补充）占位眼资产与"生命感"观感的差距 【P2】

- **缺口描述**：当前 9 帧为程序化生成的占位图（径向渐变虹膜），用户已反馈"颜色偏黄绿"；AI 美术管线（`AI_PET_EYE_AI_IMAGE_PIPELINE_zh.md`）已建但"暂缓"。
- **市场依据**：LOVOT/Ropet 的眼神质感是其溢价的直接来源（启示 5）；眼睛是本产品唯一"脸"。
- **影响**：演示说服力打折；但不阻塞交互验证。
- **建议方向**：与 G7 资产迁移**同一次完成**（新美术帧直接落 assets 分区，避免嵌入镜像再迁一次的返工）；G5 新增需求态帧一并进美术批量。
- **优先级**：P2。

## 4. 不建议做的事

- **不做聊天字幕/状态栏 UI**：双眼不显示文字（既定决策），防助手化（启示 4）；调试只走串口。
- **不堆传感器**：不上电子皮肤、多轴 IMU、温湿度阵列。触摸只做 1~3 路（摸头/抱），每多一路传感器=结构+BOM+误触面，先验证抚摸回路成立再说。
- **不做端侧 LLM/端侧 ASR 降级对话**：P4 不承担推理是既定架构；离线降级只做情绪行为（G4），不承诺离线聊天，避免制造第二个助手化入口。
- **不做连续视频流/主动摄像头上云**：视觉坚持 K230 本地推理+结构化结果；隐私叙事是差异化资产，不为功能牺牲。
- **不在固件实现人设/记忆逻辑**：演化规则、记忆召回、亲密度审计全在云端；固件只存种子与快照，守住"人设真源在云端"的分层红线。
- **不追求舵机"机器人运动"**：两路舵机只做表情性小动作（第一版约束），不做行走/舞蹈机构。

## 5. M2~M5 里程碑调整建议

当前固件里程碑：M2 双眼🟡 / M3 灯带+舵机⬜ / M4 K230 视觉⬜ / M5 体验层🟡。调整如下（变更处加粗）：

| 里程碑 | 原内容 | 调整后 |
|--------|--------|--------|
| **M1.5（新增）** | — | **工程前置包**：① G7 眼资产迁 assets 分区 + 体积门禁；② G6 误唤醒阈值 + "休息即挂断"双保险；③ G9 美术帧随迁移一次到位。出口标准：OTA 槽 <80%、拟物一致性 bug 清零 |
| M2 双眼 | 右眼接入、同步/镜像 | 内容不变；**验收加"双眼+语音 30min 无回归"**（后续规划阶段 B 已有） |
| M3 灯带+舵机 | WS2812 + 双路舵机 | **插入 G1 触摸传感器（1~2 路电容/压力）**：同属外设扩展，此时结构未冻结、BOM 可改，是最低成本窗口；触摸事件接入 `PetBehaviorController` 新 source |
| M4 K230 视觉 | UART/人脸/情绪/门控 | 内容不变；**确认触摸与人脸的优先级仲裁**（kTouch vs kVision）一并定案 |
| **M4.5（新增）** | — | **自发行为引擎（G2+G4 合并交付）**：内部状态量（精力/心情/亲密度）+ 无聊/困倦/求关注 idle 行为 + 断网离线人格兜底 + NVS 持久化。出口标准：静置 30 分钟有可观察的自发生命感；拔网线 5 分钟宠物仍"活着" |
| M5 体验层 | 眨眼/好奇/困倦小动作 | 收敛为**表达打磨**：G5 需求态资产与组合表达（lonely/expectant）、G3 随机性三层注入、G8 状态上报（待 backend 501 解除）、2h 综合老化 |

排期逻辑：G6/G7 是物理前提与当下体验止损，提到最前；G1 必须卡在 M3 结构窗口；G2/G4 不依赖新硬件，放在 K230 之后但 M5 之前，使 M5 打磨的是"一个已经活着的宠物"而非"一个会应答的设备"。
