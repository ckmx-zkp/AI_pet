# 01 — ai-pet-backend 后端接口设计缺口分析

> 用途：对照《00-AI宠物市场与竞品调研》（下称 00 文档）的六条设计启示，盘点业务后端（账号/设备/persona/记忆/分析）的设计缺口，给出优先级与排期调整建议。
> 撰写时间：2026-08-01。依据版本：backend docs/02/05/06/10/11 + 协作看板（C0+E1 已上线，其余 501 骨架）。

## 一、项目定位回顾

一句话：让 AI Pet 拥有**可版本迭代的星座×MBTI 人设**与**可审计记忆资产**，并通过 API/MCP 供给自建小智与管理台（backend docs/01）。后端是业务真源，人设、记忆、历史、分析的数据与契约都在这里。

## 二、已有设计的市场契合度

对照 00 文档"四、已覆盖"，backend 层能直接背书的四条：

| 市场验证 | backend 已有设计 | 依据 |
|---------|-----------------|------|
| 芙崽五行体系半年卖 12 万台（性格体系可卖） | 星座×MBTI 三层人设 + KB 版本化 + 钉扎/跟随（`persona_profiles.follow_latest`），比五行更纵深 | docs/02/03 |
| EchoChain 仿生记忆是留存支柱 | 可审计记忆 + candidate 人审（R3）+ 查改删全开放（R7），是 EchoChain 的可信版 | docs/04、06 |
| 离别设计是全行业盲区（启示 6） | `POST /devices/{id}/export` 已排入 E8 | docs/06、10 |
| 隐私焦虑是退货诱因之一 | 落库前脱敏只存 redacted（R2）、删除写审计、越权 404 不泄露存在性 | docs/06/08 |

结论：backend 的"人设可信 + 记忆可信"底座方向正确，市场已验证这条路；问题出在底座之上**缺"活物感"的数据与通道**。

## 三、设计缺口清单

> 编号 G1~G12。优先级口径：P0 = 不做则"情感陪伴"核心价值不成立；P1 = V0.2/V0.3 内应补齐；P2 = 重要但不阻塞当前迭代。

### G1 无"人格状态机"数据模型 —— P0

- **缺口**：数据模型 15 张表里没有任何承载宠物自身状态的表（饥饿/心情/精力/上次互动时间/被冷落时长）。宠物对服务端而言是无状态的纯配置体，"它需要我"在数据层不存在。
- **市场依据**：启示 1（被需要感 > 功能完整性；LOVOT 零功能留存最高）；00 文档"四、明确缺口"第一条。
- **影响**：persona_pack 的 `default_emotion` 只能是静态常量；冷落低落、求关注等行为无据可依；眼睛情绪联动只能随对话即时反应，无法表达"宠物此刻的状态"。
- **建议方向**：新增 `device_pet_state` 单行表（hunger/mood/energy/last_interaction_at/neglect_streak），由 chat events 与心跳驱动衰减/恢复；persona_pack 增加 `pet_state` 字段供小智注入情绪上下文。状态机规则保持极简（3~4 维、定时衰减），不做复杂仿真。

### G2 人设静态、无养成演化 —— P1

- **缺口**：`persona_profiles` 一次选定即定型，只有 KB 版本迭代（运营侧演化），没有用户侧演化——无性格成长值、无关系等级、无相处时长/互动量维度。PersonaCompiler 的输入里没有"这只宠物和主人处了多久、经历了什么"。
- **市场依据**：启示 2（不可预测性是留存关键变量；Moflin 60 天养成随机性格、二手炒价上万）。
- **影响**：第 1 天和第 180 天的宠物完全同质，复购与长期投入无抓手；"被摸透了"投诉无防御。
- **建议方向**：`persona_profiles` 增加 `bond_level` + `bond_progress`（由互动量与共同经历累计）；PersonaCompiler 按关系等级在 prompt 片段中解锁更亲密的称谓/语气/专属记忆引用。成长不做全随机（保留人设可信度），做"确定性骨架 + 小范围随机偏移"。

### G3 记忆只存不主动召回 —— P0

- **缺口**：memory MCP 三工具（search/add/forget）全部是 LLM 被动调用的工具；analyses 只有日摘要/候选提取，没有任何"在合适时机主动提起某条记忆"的触发器与编排策略。
- **市场依据**：启示 3（长期记忆是护城河，且要"主动提起你说过的事"；芙崽 EchoChain 记住生日并主动提起）；00 文档"四、明确缺口"。
- **影响**：记忆资产建得再好，用户感知不到——护城河挖了但没架桥。北极星指标中"可召回记忆条数"的"召回"环节缺失。
- **建议方向**：worker 新增 `recall_scan` 任务（按时间锚点：生日临近、上次提及 N 天、相似话题），产出 `recall_hint` 写入 persona_pack 的新字段或注入下轮会话上下文；先规则触发，不做向量召回。召回命中要写事件表，供北极星统计。

### G4 无主动触达能力 —— P0

- **缺口**：整个 HTTP API 与 internal 接口都是请求-响应模型，服务端没有任何"建议宠物主动开口"的事件通道——无主动会话建议端点、无推送、无下行队列。固件只能唤醒词触发，宠物永远不会先开口。
- **市场依据**：启示 1（LOVOT 主动行为是情感陪伴第一变量）+ 启示 5（主动靠近是非语言连接）；00 文档"四、明确缺口"第三条。
- **影响**：G1 的人格状态机即使建了也"表达不出来"；宠物只能答不能找，陪伴感天花板极低。
- **建议方向**：分两步——V0.2 先做 `GET /internal/devices/{uid}/pending_prompts` 轮询式下行（小智侧按心跳拉取，改动最小），承载"求关注/记忆召回/日运"三类主动话题；V0.3 再评估 WebSocket 下行或经 MQTT 8883 推送。固件 idle 行为属 ESP32 侧缺口，后端负责供料。

### G5 防助手化只有 taboo 字段，缺运行时防漂移 —— P1

- **缺口**：persona_pack 有 `taboo`（静态负面清单），但对话链路运行时没有任何防漂移机制：无对话质量评估、无"助手感"检测、无人设一致性反馈回路。analyses 只产摘要，不产"这轮对话像不像这只宠物"的评分。
- **市场依据**：启示 4（"助手化"是陷阱；Ropet：用户一旦当它是语音助手，期待立刻崩塌）。
- **影响**：GLM/Kimi 这类通用模型天然滑向有问必答；人设注入只在会话开头，长对话漂移无纠偏，差异化人设被稀释成通用助手。
- **建议方向**：worker 增加轻量 `persona_drift` 分析任务（抽样会话，LLM 打分 + taboo 命中检测），结果落 `analyses(kind=persona_drift)` 供 admin 查看与 KB 修订；不在实时链路加拦截（延迟与成本不允许），先离线评估 + 运营闭环。

### G6 北极星指标无埋点无统计端点 —— P1

- **缺口**：北极星"周有效陪伴互动次数 × 可召回记忆条数"没有任何数据支撑：chat events 落库但不区分"有效陪伴互动"与普通问答，记忆召回无命中事件，也无任何 metrics/stats 聚合端点（admin 侧 M4 只有分析卡片）。
- **市场依据**：00 文档"一"（35% 退货率、次月留存掉队——无法度量就无从优化）；"四、明确缺口"第七条。
- **影响**：迭代好坏只能靠感觉；留存/吃灰问题发生时无数据定位。
- **建议方向**：`chat_sessions` 增加 `interaction_kind` 分类（worker 离线打标：陪伴/问答/指令）；新增 `GET /admin/metrics/northstar`（周活设备、人均互动、召回命中率）；埋点先行，展示可从简（admin 一张卡）。

### G7 无"共同经历"数据模型 —— P1

- **缺口**：数据层只有对话记录（chat_messages）与事实记忆（memories），没有"一起做过的事"这一实体——一起看过的日出、某次出行、第 100 次对话纪念日。事件型经历与事实型记忆混淆。
- **市场依据**：启示 5（陪伴不一定是语言，共同经历是更深层连接）；Onorato"卖关系不卖产品"。
- **影响**：G2 的关系等级缺累计素材；"纪念日/里程碑"这类最强主动话题无数据源。
- **建议方向**：新增 `shared_moments` 表（kind/occurred_at/summary/linked_memory_ids），由 worker 从会话与里程碑规则（互动次数、连续天数）双路生成；作为 G3 召回与 G4 主动话题的素材库。

### G8 导出（E8）未提升到"离别设计"产品高度 —— P2

- **缺口**：export 在 docs/10 中只是 E8 收尾项（"按需"），定位为数据合规导出，未承载"硬件损坏/停产后情感延续"的产品叙事。
- **市场依据**：启示 6（离别设计是全行业盲区，数据可携带是有情感深度的差异化机会）。
- **影响**：差异化机会被降级成技术任务；导出的内容结构（是否含人格快照、共同经历时间线、可导入新设备）无人设计。
- **建议方向**：功能不必提前，但**契约与内容格式应在 V0.2 定稿**：导出包 = 人设档案 + 记忆 + 共同经历时间线 + 关系等级，格式考虑"可再导入新设备"（重绑时恢复）。这是 G1/G2/G7 字段设计的约束输入，需同步考虑。

### G9 501 骨架面仍大，联调原料未通 —— P0

- **缺口**：除 auth+devices 外，persona/messages/memories/analyses/peripheral/admin KB/internal 四接口全部 501（协作看板集成点状态全"骨架"）。设备已在真实对话，语料每天在流失。
- **市场依据**：工程现实，非市场缺口；但它阻塞 G1~G7 的一切——没有旁路数据，记忆/召回/指标都无米下锅。
- **影响**：xiaozhi V0.2 集成（persona_pack/旁路/MCP）全阻塞；admin M2~M4 空态等待。
- **建议方向**：维持 docs/10 排期与看板 P0 共识：E2 人设链 → E3 旁路 → E4/E5/E6，不在此期间插入新产品功能。

### G10 Memory MCP 传输方式未定 —— P1

- **缺口**：memory-mcp 当前是 stdio 骨架，xiaozhi 侧消费需要 stdio+mcp-proxy 桥接；看板待决"建议改 HTTP MCP"，docs/05 契约未更新。
- **市场依据**：工程现实。
- **影响**：记忆工具是 G3 召回能力的前置；传输不定，xiaozhi 侧无法开工。
- **建议方向**：按看板会话 B 建议改 HTTP MCP（streamable-http），先改 docs/05 契约再改实现（协作规则），E5 内完成。

### G11 成本与配额计量缺失 —— P1

- **缺口**：worker 调外部 LLM（GLM/Kimi）做摘要/候选提取，无任何用量计量与配额设计——无 per-device 任务限频、无 token 用量记录、无成本看板。agent_tasks 队列表无重试预算/降级策略字段。
- **市场依据**：工程现实；00 文档"一"（赛道放量，用户量上来后 LLM 成本是主要可变成本）。
- **影响**：多设备上线后摘要/分析任务成本不可控；无配额则单设备异常可拖垮队列。
- **建议方向**：`agent_tasks` 增加 attempts/max_attempts；worker 记录每次 LLM 调用 token 用量到独立表；per-device 每日任务配额（如摘要 1 次/天、候选提取限频）写死默认值，不做配置系统。

### G12（补充）设备在线/心跳数据未用于"冷落"计算 —— P2

- **缺口**：docs/06 已定在线状态镜像 `online_at`，但该字段只用于列表展示，没有反哺任何产品逻辑（宠物是否被冷落、用户流失预警）。
- **市场依据**：启示 1；00 文档"一"（次月留存掉队是行业通病，流失预警是运营抓手）。
- **影响**：G1 的 neglect 维度缺数据源；运营无法发现"已吃灰"设备。
- **建议方向**：E3 心跳落地时即按 G1 的 `device_pet_state.last_interaction_at` 一并写入；admin 侧流失预警列表排 V0.3。

## 四、不建议做的事

结合 00 文档市场教训与 docs/01 非目标清单，明确拒绝范围膨胀：

- **不做实时下行推送基建（MQTT/长连接）进 V0.2**：docs/01 非目标已排除实时音频通道；G4 用轮询式 pending_prompts 起步，8883 推送留 V0.3 再评估。
- **不做全随机性格生成（Moflin 式 400 万种）**：与本项目"可审计、可版本化人设"的定位冲突；随机只做钉死人设上的小偏移，骨架确定性必须保留。
- **不做向量记忆检索 / 每条消息 embedding**：看板"明确不做"已列；G3 召回用规则+时间锚点足够，向量是成本与复杂度的坑。
- **不做触摸/体温等硬件传感的服务端预留**：属固件与硬件缺口（见 04 文档），backend 不为未立项硬件先建表。
- **不做通用对话质量平台**：G5 只做离线抽样评分 + admin 可见，不做实时拦截、不做 A/B 编排框架。
- **不做社交裂变/好友 Feed**：docs/01 非目标已排除；docs/11 设备 BLE 社交（E9）是既定 V0.3 范围，到此为止不扩大。
- **不做重型星历/日运引擎**：非目标已列，日运保持短上下文生成。

## 五、对 E2~E8 排期的调整建议

原则：docs/10 的 E2→E3→E4/E5/E6 主链不动（联调原料优先，看板 P0 共识）；新缺口以"伴随式小改动"插入，不新增阻塞性 Epic。

| 调整 | 插入点 | 理由 |
|------|--------|------|
| **G10 HTTP MCP 契约定稿** | E5 前置动作（改 docs/05） | 已有看板共识，只是落地 |
| **G1 `device_pet_state` 建表 + 心跳驱动** | 随 E3 迁移一并建表，E3 心跳写入时填 `last_interaction_at`；状态衰减任务随 E6 worker | 表早建无成本（docs/11 的社交两表已是"提前建掉"先例）；衰减逻辑后置不阻塞 |
| **G2 `bond_level/bond_progress` 字段** | 随 E2 的 persona 迁移加列（先只累计不消费），PersonaCompiler 消费排 V0.3 | 加列成本极低，后补则要数据回填 |
| **G6 埋点字段（`interaction_kind`）+ 召回命中事件** | 打标任务随 E6 worker；`/admin/metrics/northstar` 端点排 E7 后 | 埋点先行、展示从简 |
| **G3 recall_scan + G7 `shared_moments`** | V0.3 新 Epic（E10），依赖 E5/E6 产物 | 需要记忆与摘要数据积累后才有效 |
| **G4 pending_prompts 轮询端点** | V0.3 与 E10 同批（契约需同时改 xiaozhi docs/05） | 依赖 G1/G3 供料；需小智侧配合 |
| **G5 persona_drift 离线评分** | V0.3，E6 worker 稳定后 | 需要真实语料量 |
| **G8 导出格式契约定稿** | E8 之前、V0.2 内完成格式设计（实现仍在 E8） | 格式是 G1/G2/G7 字段设计的约束，晚定会返工 |
| **G11 任务配额与 token 计量** | 随 E6 worker 一并实现 | 与 worker 同代码面，顺手做；不做配置系统 |
| **G12 流失预警** | V0.3 admin 侧 | 依赖 G1 数据 |

调整后 V0.2 的净增量 = 3 张表/若干加列（pet_state、bond 字段、埋点字段）+ MCP 传输变更 + worker 计量，估 <15% 工作量；主动召回、主动触达、防漂移、共同经历四个"活物感"主体统一进 V0.3（E10）。
