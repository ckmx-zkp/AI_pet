# ai-pet-admin（Web 管理台）设计缺口分析

> 同系列：`00-AI宠物市场与竞品调研.md`（市场输入，本文以"启示N"引用其六条设计启示）。
> 分析基线：ai-pet-admin docs/00~07 + `api-openapi.json`（25 端点，除 auth 外多为 501）+ `work_dashboard/AI-Pet协作看板.md`（M1 已公网上线）。
> 调研时间：2026-08-01。

## 一、项目定位一句话回顾

ai-pet-admin 是 AI Pet 系统的**第一 UI**：给开发者/运营"调人格、喂知识、看脑子"的控制面板——管设备、定人设（星座×MBTI）、审记忆、发 KB，不面向最终消费者（docs/07）。

## 二、已有设计的市场契合度

对照调研文档"四、与 AI Pet 现有设计的对照"，admin 侧已走在正确路上的部分：

- **人设页是核心页而非附属页**（docs/02 标注"V0.2 核心"）：星座×MBTI 三层人设 ≈ 芙崽五行的纵深版，市场已验证这条路能卖；`follow_latest` + `kb_version` 展示说明版本化意识已进入 UI 规格。
- **记忆 candidate 人审**（通过/驳回）≈ EchoChain 的可信版，"记忆可查可删"直击隐私焦虑，且审核权限只放 admin 角色，边界正确。
- **KB draft→published 版本化发布 + 反馈候选接受/忽略**：Agent 夜间产出 → 人审闭环，运营侧职责划分清晰（用户 App 明确不做）。
- **数据导出入口已规划**（docs/02 系统页）：启示 6"离别设计"的行业空白，我们已有种子。
- **外设状态只读页**（emotion/gaze）：承认"眼睛生命感"是 LOVOT/Ropet 眼神系统的低成本实现，并给它留了观测窗。
- **克制的非目标清单**（不做日记 Feed/成长曲线/社交）：与"管理台优先于消费 App"的阶段判断一致，避免与 ai-pet-app 职责混淆。

## 三、设计缺口清单

> 每条含：缺口描述 / 市场依据 / 影响 / 建议方向 / 优先级（P0=阻塞核心价值验证，P1=运营闭环必需，P2=可后置）。
> G1~G8 为产品方已识别缺口，G9 为本次分析补充。

### G1 无 persona_pack 编译预览（dry-run）

- **缺口描述**：人设页保存的是星座+MBTI+忌口等"原料"，真正下发的是 backend PersonaCompiler 编译出的 persona_pack。当前 UI 只有"保存→下次会话生效"，运营保存前看不到编译结果。
- **市场依据**：调研"四"已确认人设体系是核心卖点；启示 4 指出人设编排质量直接决定"是宠物还是助手"。
- **影响**：运营调人设是盲调——忌口是否生效、口吻是否符合星座差分，只能开一台真机对话才知道；"盲测口吻"这一验收动作没有任何工具支撑，迭代周期以"天"计。
- **建议方向**：backend 增加 `POST /devices/{id}/persona/compile-preview`（不落库，返回编译后 persona_pack 全文 + 可选的 1~2 条样例回复）；admin 人设页加"预览编译结果"抽屉，diff 当前生效版与预览版。
- **优先级**：**P0**（M2 人设页点亮的同时就该有，否则 M2 交付的是一个不可验收的页面）。

### G2 无人格状态/宠物"心情"可视化

- **缺口描述**：外设页只读展示 emotion/gaze 硬件状态，但没有"宠物当前虚拟状态"（饥饿/心情/精力/多久没被搭理）的观测入口。
- **市场依据**：**启示 1**（被需要感 > 功能完整性，LOVOT 零功能却留存最高）；Moflin"冷落它会低落"。
- **影响**：人格状态机是全项目级缺口（调研"四"已列），admin 作为"看脑子"的面板，连宠物当下"开不开心、有没有被冷落"都看不到，运营无法验证"被需要感"机制是否真的在运转——机制做出来也是黑盒。
- **建议方向**：依赖 backend 先定义人格状态模型（属全项目缺口，见 01/03 文档）；admin 侧在设备详情页加"当前状态"卡片（状态值 + 最近状态变更时间线）。admin 不做状态编辑，只观测。
- **优先级**：**P1**（依赖上游状态机先存在，但 UI 成本极低，应随状态机落地同步点亮）。

### G3 北极星指标无看板

- **缺口描述**：项目北极星 = "周有效陪伴互动次数 × 可召回记忆条数"，admin 没有任何统计/仪表盘页面。
- **市场依据**：调研"一"：行业核心矛盾是退货率与"吃灰"，留存数据是生死线；调研"四"明确"北极星指标无法度量"是全项目缺口。
- **影响**：V0.2 上线后无法回答"宠物有没有被用起来"，所有运营决策（人设调整、KB 迭代）无反馈回路；这也是 35% 退货率行业通病在自家产品上的盲区。
- **建议方向**：backend 出最小统计端点（如 `GET /devices/{id}/stats/weekly`：会话次数/有效互动定义/新增与召回记忆条数）；admin 加单设备"概览"卡，不做全站 BI。注意 docs/05 工程纪律"M4 之前不要图表库"——首版用纯数字卡片即可，不引 ECharts。
- **优先级**：**P1**（不阻塞 M2~M4 开发，但阻塞"V0.2 是否成功"的判断；建议插入 M4 之后立刻做）。

### G4 记忆审核缺"记忆质量"视角

- **缺口描述**：记忆页只有 candidate 通过/驳回（存量视角）。没有"这条记忆后来被主动召回过吗、召回时对话效果如何"（使用视角）。
- **市场依据**：**启示 3**（长期记忆是护城河，且要"主动召回"）；调研"四"：memory.search 是被动工具，缺主动召回编排。
- **影响**：审核通过的记忆可能从未被召回，或召回时语气生硬反而扣分——运营无法区分"存了一堆死记忆"和"记忆真的在产生情感价值"；护城河深度不可度量。
- **建议方向**：backend 在记忆模型上加召回计数/最近召回时间（需先在召回链路上打点，属上游缺口）；admin 记忆列表加"召回次数/最近召回"列并支持排序，让"高召回记忆"和"死记忆"一眼可辨。
- **优先级**：**P1**。

### G5 KB 反馈审核有闭环，缺"人设漂移"监测入口

- **缺口描述**：KB 反馈候选（接受/忽略）处理的是"知识缺什么"，但没有监测"线上对话是否滑向通用助手"的入口——用户问天气问穿搭被正经回答时，系统无感知。
- **市场依据**：**启示 4**（"助手化"是陷阱，Ropet CEO：用户一旦当它是语音助手期待就崩）；调研"四"：persona_pack 有 taboo 字段，但缺运行时防漂移机制——admin 侧同样缺观测端。
- **影响**：人设漂移是慢性病，发现时往往已积累大量"助手味"对话语料并反向污染 KB 反馈候选；运营没有早期信号。
- **建议方向**：轻量起步——backend 夜间分析（daily_summary 同类 worker）对对话打"疑似助手化"标记（命中天气/穿搭/百科类意图且未按人设化解），admin 在分析页加一类"漂移预警"只读卡片 + 跳转对应历史记录。不做实时拦截（那是 xiaozhi-server 编排层的事，本仓不在实时路径上，docs/07）。
- **优先级**：**P1**（P2 亦可接受，取决于对话语料积累速度）。

### G6 无 A/B 或灰度工具

- **缺口描述**：`follow_latest` / 钉扎 `kb_version` 的数据模型已存在（人设页规格），意味着 backend 天然支持"不同设备跑不同 KB 版本"，但 UI 只有单设备的开关，没有多版本对比/灰度视角。
- **市场依据**：**启示 2**（不可预测性是留存关键变量，性格不该一次定型）——人设迭代本身需要实验机制，否则"优化人设"只是拍脑袋全量发布。
- **影响**：KB 每次发布即全量生效（follow_latest 的设备），出问题只能回滚版本，无法小流量验证；人设改版效果无对照。
- **建议方向**：不建完整实验平台。最小形态：KB 发布页展示"各版本在役设备数"（follow_latest vs 各钉扎版本的分布），发布前提示影响面；人设页保留钉扎即可。真正的 A/B（按设备分组+指标对比）等 G3 统计端点落地后再评估。
- **优先级**：**P2**（内测期设备量级小，发布影响面提示即可满足）。

### G7 离别/导出只是入口，缺"用户数据资产"视角

- **缺口描述**：导出只有系统页一个"（可选）导出入口"（docs/02），没有"这只宠物积累了什么"的资产总览——多少条记忆、多少天对话、KB 版本沿革、可导出内容清单。
- **市场依据**：**启示 6**（离别设计是全行业盲区，数据可携带/记忆可迁移是有情感深度的差异化机会）；调研"四"确认 E8 导出已规划是"种子"。
- **影响**：种子没浇水。硬件损坏/换机是硬件产品的必然事件，届时用户（当前=内测者）第一反应就是来管理台找"我的数据还在吗"，现在没有页面能回答这个问题。
- **建议方向**：设备详情加"数据资产"区块：记忆条数、对话天数、最近活跃、导出入口与导出内容说明（含记忆、历史、人设配置）；导出格式在人类可读性上做要求（不只是 JSON dump）。依赖 backend E8（C4 数据导出，协作看板排 P2）。
- **优先级**：**P2**（随 backend 导出端点落地同步做，不宜再晚——它是差异化卖点而非成本项）。

### G8 工程现实：M2~M4 全部阻塞在 backend 501；外设页只读

- **缺口描述**：openapi.json 25 端点中仅 auth 3 个可用，devices 刚随 E1 点亮，persona/messages/memories/analyses/peripheral/admin-kb 全部 501；外设页即使点亮也只读（emotion/gaze 无写接口）。
- **市场依据**：—（工程项，无直接市场依据；但协作看板"开发优先级"已指出：backend 每晚一天，旁路语料就多丢一天，admin 各页就多空转一天）。
- **影响**：admin 已公网上线但只有壳；更隐蔽的风险是——前端按契约开发完成后长期不联调，契约与实际实现的偏差会在 M2~M4 集中爆发。
- **建议方向**：维持"按契约开发 + 501 空态自动点亮"策略（docs/05 §3.2，该策略正确）；每点亮一个后端端点立刻真联调并回看板记录偏差；外设页保持只读定位（调试写操作属小智智控台，外链即可，不越界）。
- **优先级**：**P0**（这是所有其他缺口落地的前置条件；但对 admin 本仓而言是"等+联调"，不是设计工作）。

### G9（补充）user 与 admin 同池，缺最小权限与审计视角

- **缺口描述**：角色模型只有 user/admin 两档（docs/01），admin 账号"待后端提供"（docs/05 §3.3）。KB 发布是全局生效的高危操作，但 UI 规格里没有发布确认、发布记录/操作审计的展示入口。
- **市场依据**：—（工程与运营安全项）；对照 G6：无灰度时，发布操作的安全网就只剩"可回滚+可追溯"。
- **影响**：内测期多人共用一个 admin 账号时，误发布无法追责、无法回答"谁在几点发了哪个版本"；CORS/公网已开（8080 直连），攻击面是真实的。
- **建议方向**：KB 发布加二次确认 + 发布历史列表（版本号/操作人/时间，数据大概率 backend 已有审计字段）；admin 账号尽快独立下发，不共用。
- **优先级**：**P1**（M4 KB 页开发时顺手做，成本极低）。

## 四、不建议做的事（防范围膨胀）

以下事项有市场诱惑或竞品先例，但**不应进入本仓**：

- **不做消费级 Feed/日记/成长曲线**：docs/00、docs/05 已三次明确列为非目标；情感陪伴体验层属于 ai-pet-app，管理台做了只会两头不靠（启示 5 的"无声陪伴"体验尤其不该塞进表单型管理台）。
- **不做用户端功能**：KB 发布、反馈审核是运营职能，明确不进 ai-pet-app（docs/00）；反过来用户侧的人设"盲测口吻"聊天窗也应留在 ai-pet-app，admin 只做 G1 的编译预览（看文本），不做真机对话模拟器。
- **不复刻小智智控台**：模型供应商、ASR/TTS 参数、底层智能体调试一律外链（docs/00）；外设页保持只读，不做固件级写操作。
- **不做全站 BI / 图表平台**：G3 北极星指标用数字卡片起步；docs/05 明确"M4 之前不要图表库"，即使 M4 后也应先证明指标口径有用再引图表库。
- **不做完整 A/B 实验平台**：G6 已述，内测期设备量级配不上实验平台成本。
- **不做社交/NFC/儿童模式**：母文档与 docs/01 非目标清单已排除，调研中 BubblePal/FoloToy 的儿童向路线与本项目"桌面陪伴"定位不同。

## 五、M2~M4 之外的里程碑建议

将上述缺口映射到里程碑（现有：M2 人设 / M3 历史+记忆 / M4 KB+分析+外设）：

| 缺口 | 建议落点 | 理由 |
|------|---------|------|
| G1 编译预览 | **插入 M2** | 没有它 M2 不可验收；需 backend 同步出一个 dry-run 端点（小，纯编译不落库） |
| G9 发布确认+历史 | **插入 M4** | KB 页开发顺手项 |
| G3 北极星看板 | **新 M5（运营观测）首选** | 依赖统计端点，且是判断 V0.2 成败的前提，应排在其他锦上添花项之前 |
| G4 记忆召回视角 | M5 | 与 G3 共用"召回打点"上游工作，一并做 |
| G5 漂移预警 | M5 或 M6 | 依赖 nightly worker 打标，语料少时价值低 |
| G2 人格状态卡片 | M5（若上游状态机就绪）否则 M6 | UI 成本极低，瓶颈在上游模型定义（全项目缺口） |
| G6 版本分布提示 | M6 | 先只读展示，A/B 后置 |
| G7 数据资产区块 | **随 backend E8 导出端点同步**（不单独占里程碑） | 差异化卖点，不宜晚于导出端点本身 |

**M5 建议定义（运营观测里程碑）**：单设备概览卡（北极星两因子 + 数据资产摘要）+ 记忆召回列 + 漂移预警卡片。一句话：M2~M4 让运营"能操作"，M5 让运营"能看见效果"——对应调研"一"的行业生死线（留存/吃灰）从不可见变为可度量。
